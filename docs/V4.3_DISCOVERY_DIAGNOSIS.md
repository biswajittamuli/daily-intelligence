# V4.3 job discovery: diagnosis and technology selection

Audit of 4.2.0 (commit e376385) against the real database (schema 10, 185 stored listings,
last full discovery run 2026-11-09 09:46 UTC). Written before any code change.

## 1. Root causes

| # | Symptom | Exact cause (file) |
|---|---------|--------------------|
| A | Ametek "AI Engineer / Developer" shown as *seen today* | The listing came from a web-search **snippet** (`extraction_method = search result snippet`, `posted_date = NULL`). `freshness_bucket` (`services/freshness.py`) falls back to `first_seen` and returns "First seen today" with key `new_today`; `rowMeta` in `static/js/home.js` rewrites it to "seen today" and the feed counts it as *new*. Re-verification fetched the page through the search provider (`verification.py`, provider path), found an apply button and marked it open, but that path never reads a posting date. The page states `Date: Oct 19, 2026` (21 days old). Nothing parses label-style dates ("Date:", "Posted on"). `jobs.ametek.com` is the employer's own domain but was not treated as an employer page, so the JSON-LD/direct path was not used. |
| B | "Remote Professionals & Specialists – AI Matching Network" scored 99 (strong) | No document-type classification exists. Hasjob feed entries are all treated as `job_listing`; `relevance_gate` only rejects search-result URLs and non-technical titles. The record has no employer and no single vacancy, yet goes straight to resume scoring. |
| C | San Francisco / New York / other non-India jobs in the feed | `location_fit` (`services/job_matching.py`) **fails open**: (1) a location of just "Remote" → fits; (2) any `remote` flag plus a place not in the `FOREIGN_PLACES` regex ("Remote - Luxembourg", "Malaysia, Malaysia", "Hong Kong") → fits; (3) no location → unknown → passes. Career-page link harvesting stores the city inside the title ("AI Platform Engineer San Francisco San Francisco Apply") with `location = NULL`, so case (3) admits it. `geo.work_arrangement` maps "Remote" + "Global"/"APAC" to "Remote from India". |
| D | LinkedIn / Indeed / Naukri / Indian portals missing | (1) Policy: LinkedIn, Indeed, Glassdoor, Naukri, Wellfound and YC Work at a Startup are *search-results-only* (their terms forbid automated access); only the search provider's index is used, and Parallel returns 0–5 hits for `site:` queries on them. (2) Budget: a 100-pool run makes 8 search calls interleaved over 7 query groups, so only one or two portal batches run; **14 of 21 portals were never queried** (foundit, Instahyre, Cutshort, Hirist, TimesJobs, Freshersworld, Internshala, Apna, Shine, iimjobs, WorkIndia, YC Jobs, Talent.com, Hasjob-as-portal). The portal list never rotates between runs. (3) No job-API sources exist besides ATS boards and the Hasjob feed. |
| D2 | "16 of 23 sources answered" | The 7 non-successful sources: Ashby *partial* (some boards 404); Indeed, Naukri, Wellfound *partial* only because the search-only policy text is recorded as a failure reason; LinkedIn, startup.jobs, index-page expansion *no results*. Meanwhile six `search:*` sources are marked **successful with 0 listings extracted**: success means "HTTP answered", not "usable vacancies". Hasjob is registered twice (`feed:hasjob` and `portal:hasjob`). |
| E | Search results / talent pages treated as vacancies | Only `looks_like_index` (URL/title heuristics) exists; no classifier for talent networks, candidate registration, careers home pages, agencies, articles or company news. |
| F | `&amp;` in titles | Career-page link titles and feed titles are never HTML-unescaped (`Software Engineer – Backend &amp; Platform`, `View &amp; Apply`). |

Other findings:
- Ranking happens before any validity check. `_rank_candidates` → `relevance_gate` → `assess`; vacancy type, geography certainty and verification never cap the tier.
- 10,004 raw records → 6,017 unique → 143 stored. 3,128 were rejected for location: the default ATS employer list is dominated by US companies. This is acceptable once geography is classified correctly; Indian sources need to be added instead.
- Cross-source dedup keys on (normalised title, employer) only, so two openings with the same title in different cities merge.
- Status transitions are kept only in `verify_history_json` (20 entries) and have no table.

## 2. Implementation sequence

1. Dates: publication-based freshness buckets only; first-discovered shown separately; label dates ("Date:", "Posted on", microdata) parsed; employer-domain pages verified directly; dates captured during verification.
2. Document classifier (14 types) as the gate before ranking; talent networks go to their own section.
3. Geography classifier (6 categories + location unknown), fail-closed and configurable (`jobs.target_country`), used as a hard filter and in the feed.
4. Source health: success means usable vacancies; search-only portals report a policy state instead of failure; per-source vacancy, unique, verified and rejected counts; `sources-report` CLI.
5. Portal coverage: rotating portal batches so every portal is queried over consecutive runs; new API adapters (below); LinkedIn, Indeed and Naukri reached through Google for Jobs (SerpApi, optional key).
6. Employer verification: employer-owned domain detection; JSON-LD, label dates and `validThrough`; a timeout never closes a job.
7. Dedup: city and requisition id in the identity; employer URL preferred; every source kept.
8. Ranking/feed: validation result groups (verified strong/good, stretch, pending, outside geography, not a vacancy, closed); the main feed shows only verified-open, in-geography vacancies.
9. Regression tests for the ten required cases, then a real discovery run.

Schema v11 (additive, backed up automatically): `job_listings` gains `document_type`, `geo_class`,
`vacancy_status`, `verification_level`, `validation_json`, `last_fetched_at`; new table `job_status_history`.

## 3. Technology selection

Research date 2026-11-09. Quotas come from vendor and third-party pages and change often; each paid or keyed
provider is optional and reports "not configured" without a key.

| Tool / API | Purpose | India coverage | Cost / free tier | Limitations | Decision |
|---|---|---|---|---|---|
| Parallel MCP (existing) | Web search + fetch | Good for open web, weak for portal `site:` queries | Free tier, rate-limited | Few LinkedIn/Naukri hits | **Keep** as the primary search provider |
| Himalayas public API | Remote jobs with explicit `locationRestrictions`, `pubDate`, `expiryDate` | Verified live: 337 ML jobs with `country=India`, many restricted to India | Free, no key; attribution requested | Remote only; robots.txt disallows `&page=`, so page 1 only per query | **Integrate** (default on) |
| Adzuna API | Aggregated Indian job market (`/jobs/in/search`) with `created` dates | India is a supported country | Free developer key (reported ~250 calls/day; check the portal) | Redirect links go through Adzuna; snippets truncated | **Integrate, optional** (`ADZUNA_APP_ID`, `ADZUNA_APP_KEY`) |
| SerpApi Google Jobs | Google for Jobs results, which index LinkedIn, Naukri, Indeed, foundit, with `via` and apply links | Google Jobs covers India (`gl=in`) | 250 searches/month free (raised from 100 in 2025) | Monthly quota; relative dates ("3 days ago") | **Integrate, optional** (`SERPAPI_API_KEY`): the compliant route to LinkedIn, Indeed and Naukri listings |
| Jooble API | Aggregator | Unconfirmed for India | Free key on request; reportedly 500 lifetime requests per key | POST only; small cap | **Reject for now** |
| Arbeitnow | Aggregator | Europe-focused | Free | Little India content | **Reject** |

Why APIs over custom scraping: Himalayas, Adzuna and Google Jobs return structured title, company, location,
publication date and links with documented permission. A scraper for the same portals would break on markup
changes and, for LinkedIn, Indeed and Naukri, would breach their terms.
